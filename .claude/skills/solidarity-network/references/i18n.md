# Translations (PHP + JS)

Two separate translation systems that look alike and behave differently. Most of the pain here
comes from assuming a fix in one applies to the other.

> **Page translation groups.** The variants of one page share a `translationGroupId`, and
> `PageRepository::createTranslation()` puts **both** the source and the new page into it —
> reusing the source's existing group when it has one, so a third locale doesn't split the
> set. It previously stamped only the translation and left the source `NULL`; since
> `PageAction::setLocalizedSwitcher()` looks up `getLocalizedSlugs($page->translationGroupId)`,
> neither page could find the other and both fell back to the homepage. `PageActionTest` did
> not catch it because its fixtures assign one group id to both pages by hand. Any pair
> created before the fix still has a `NULL` root — backfill with:
>
> ```sql
> UPDATE page p JOIN page t ON t.translationGroupId = p.id
> SET p.translationGroupId = p.id WHERE p.translationGroupId IS NULL;
> ```

## Two systems

| | PHP | JS |
|---|---|---|
| Call | `t('String')` / `$this->translator->translate(...)` | `Translator.translate('String')` |
| Source | `translation` table (Redis-cached) | generated `translations.js` module |
| Default locale | **pass-through** — returns the key unchanged | `BASE_LANGUAGE = 'en'` |

**Keys are the English string** in both. The `translation` rows store Serbian in
`originalString` and English in `translatedString`, so the JS export is configured with
`'jsInvert' => true` (`config/config.php`) to key the generated file by the English string:
`{"Delete": {"sr": "Obriši"}}`.

Consequence that catches people out: **a missing JS translation shows the English string, and
a missing PHP translation shows the key** — which is also English. So an untranslated string
looks fine on `/en` and only breaks on the Serbian site. When a translation bug is reported,
check the *other* locale before assuming the string isn't wrapped.

## The language row

`t()` returns nothing useful — every call degrades — if the `language` table is empty or
contains only `en-us`. It needs a proper row. Symptom is global and total: every translated
string on the site goes blank or falls back at once, which reads like a cache or template bug
rather than a data one.

Translator cache key: **`skeletortranslations#2#`**. (Keys beginning `91dd0*` in the same Redis
belong to a WordPress co-tenant — not ours, don't clear them.)

## Commands

```bash
php public/cli.php resetTranslationsCache run     # after a manual `translation` table edit/import
php public/cli.php exportTranslations run         # regenerate translations.js from the table
php public/cli.php importJsTranslations frontend  # scan JS for translate('...') → idempotent SQL
```

Admin edits regenerate `translations.js` automatically; the export command is for after a
**manual SQL import**. `importJsTranslations backend|frontend` scans an asset tree for
`translate('...')` calls and emits SQL with empty translations for you to fill in — that's how
`data/js_translations_frontend_wrapped.sql` was produced.

The export writes the *same* module to both asset trees
(`public/assets/{backend,frontend}/js/config/translations.js`), and only emits the languages in
`translator.jsLanguages` (currently `['sr']`).

## Gotchas

- **Bump the `?v=` query string** on any JS you touch, including `global.js`. The box serves
  assets cached and a translation fix that isn't visible is usually a stale file, not a
  missing row.
- `isEnglish` in `global.js` must test `pathname === '/en' || pathname.startsWith('/en/')`.
  A bare `includes('/en')` matches things like `/enrollment`.
- Status labels and other strings built in **services** need the `Translator` injected — e.g.
  `DonorService` takes it as its 14th constructor argument purely for the status label. In
  tests, a bare `Translator` stub returns `''` and the label silently disappears; stub it with
  `->willReturnArgument(0)`.
- Serbian text lives in the codebase in places (validator messages, the `NoNeedsException`
  ladder, the XLSX headers and its `"Plaćeno,Neplaćeno"` dropdown). Those are not wrapped and
  mostly shouldn't be — the XLSX ones are a data contract with the upload parser, not UI copy.
