# Operations, apps, auth & migration

Infrastructure and cross-cutting concerns added beyond the core CRUD domain.

## Two apps, one bootstrap (`APPLICATION` env)

`public/index.php` reads `getenv('APPLICATION')` (`frontend` | `backend`) but loads the **single** `config/bootstrap.php` for both. nginx sets `APPLICATION` (and `APPLICATION_ENV`) per vhost: **solidarityadmin.local = backend**, **solidarity.local = frontend**. Routes are split: `config/backend/routes.php`, `config/frontend/routes.php`. Logs are per-app (`data/logs/vagrant-frontend-*.log`, `vagrant-backend-*.log`).

**Read these two env vars through `Solidarity\Core\Environment`, not raw `getenv()`.** It's the single source of truth (`packages/Core/src/Environment.php`, namespace registered in `composer.json` — a new prefix needs `composer dump-autoload`): `Environment::isFrontend()` / `isBackend()` / `application()` for `APPLICATION`, and `Environment::isProduction()` / `name()` for `APPLICATION_ENV`. Reads are lazy + lower-cased, so the magic strings (`'production'`, `'backend'`) and case-normalisation live in one place. Chosen over a `constants.php` constant because **`cli.php` does not load `constants.php`** — a constant would be undefined (fatal) in cron, where the `Mailer` env guard runs; the class is autoloaded by both web and CLI entrypoints. bootstrap, `public/index.php`, and `Mailer` all go through it.

**Gotcha that bites hard:** `bootstrap.php` has an `if (\Solidarity\Core\Environment::isBackend()) { ... }` block. Anything bound only inside it is **absent on the frontend** → DI autowires an empty/uninstantiable object → cryptic errors ("Unknown entity type: donor", "ProviderInterface not instantiable"). When a frontend flow needs an auth binding, **move it out of that block** (it stays available to both). Already moved out for donor auth: `EntityRegistry`, `ProviderInterface` (`DbProvider`), `ResetPasswordInterface`. Keep genuinely backend-only things (e.g. `PermissionRegistry`, which reads `backend/permissions.php`) inside.

**OPcache:** editing `bootstrap.php`/config does **not** take effect until FPM reloads the compiled file. After bootstrap/config edits: `sudo systemctl restart php8.4-fpm`. For dev, set `opcache.validate_timestamps=1` + `opcache.revalidate_freq=0` in an FPM `conf.d` ini so edits apply live. (This caused several "my change isn't working" dead-ends.)

## Donor magic-link auth (frontend)

`Donor` is an **authenticatable entity** (`implements AuthenticatableInterface`, `ROLE_DONOR = 20`, magic-link only). Wiring:
- `DonorRepository implements LoginRepositoryInterface` (`findByEmail` etc.).
- Registered in `EntityRegistry` as `'donor'` (bootstrap, top-level — see above).
- `Donor::isActive()` returns true for `STATUS_NEW` and `STATUS_VERIFIED` so an unverified donor can receive + click the first link (the click *is* the verification).

Frontend actions (`packages/Frontend/src/Action/Donor/`): **Register**, **VerifyEmail**, **Login**.
- Register → `Donor::create()` (throws on duplicate email — not an upsert) → `requestMagicLink($email, 'donor', false)` returns the token → `Mailer::sendDonorRegisteredMail()` (custom "verify your email" template).
- Login → `Donor::requestLoginLink($email)` (silent if email unknown — no enumeration) → `Mailer::sendDonorLoginMail()` (reuses the `magicLink` template).
- VerifyEmail (shared by register + login) → reads token from the **query string** (`?token=…`, route `/donor/verifyEmail`) → `MagicLinkCredentials($token, 'donor')` → `AuthenticatorRegistry::authenticate()` → flips `NEW → VERIFIED` → `LoginService::login($donor, 'donor')`.

**Why custom mail instead of the framework's `requestMagicLink(..., true)`:** the framework's `buildMagicLinkUrl()` hardcodes `adminUrl/login/{type}/verifyMagicLink/{token}` — wrong domain/path for a frontend donor. So we pass `sendMail=false`, get the token, and build `{baseUrl}/donor/verifyEmail?token={token}` ourselves. The clean long-term fix is in the `skeletor` skill TODO (config-driven `buildMagicLinkUrl`). When reusing the `magicLink` email template, pass the URL under the **`loginUrl`** key (not `magicLinkUrl`) or the button href is empty.

## Mail catching (Mailpit)

The app sends via **MailerSend (HTTP API)**. The app `Mailer` (`packages/Mailer/src/Service/Mailer.php`) overrides `send()`: `Environment::isProduction()` → MailerSend; otherwise **catches via SMTP** (PHPMailer → Mailpit). `MailerInterface` is bound (bootstrap) to the **app `Mailer`** (not the framework's `MailerSendMailer`) so *every* path — including the framework login flow — goes through the guard. The MailerSend SDK is built with a **placeholder api_key** when none is configured, so the app boots locally without a real key.

- **Dev (per Vagrant box):** Mailpit installed in `bootstrap.sh`; web inbox **http://192.168.25.43:8025**, SMTP `127.0.0.1:1025` (config `mailer.smtp`).
- **Shared dev/test server:** in-memory, `--max-age 1h`, bind `127.0.0.1`, exposed via OLS reverse proxy + basic auth. See `deploy/` notes if added.

## Cron (CLI actions)

`CliSkeletor` invokes any cliMap class whose name contains `Action` via `__invoke($request,$response)`; mapped in `config.php` `cliMap`. Committed crontab: **`deploy/crontab`**.
- Donation allocation: `php public/cli.php createTransactions run` → `Solidarity\Backend\Action\CreateTransaction`.
- The crontab sets `APPLICATION_ENV=production` (cron doesn't inherit nginx fastcgi params) so cron mail goes through MailerSend.

## Legacy data migration

Old app is the Symfony 6.4 **solidaritySF** at `C:/radno/solidaritySF` (single-project; amount/account stored inline on entities). Migration command: `Solidarity\Backend\Action\MigrateLegacy` (`php public/cli.php migrateLegacy run` = dry-run/report, `… commit` = real). Reads a separate `legacyDb` (config-local) via DBAL, writes the new entities in dependency order, hardcodes the **MSP project (id 1)**, treats all old data as **bank transfer**, and **preserves original `created_at`/`updated_at`** via a raw-SQL pass (Timestampable is `insertable:false`). Mapping highlights: **`DamagedEducator → Beneficiary` is many-to-one** — the legacy app stores one `damaged_educator` row per (person × period) with the account repeated, so the migration **groups those rows by person** (key = `account_number`, falling back to `name`+`school`) into a single `Beneficiary` with one `PaymentMethod` and many `RegisteredPeriods` (one per period-row). Every old row id still maps to the merged beneficiary so transactions resolve, and a person is marked active if any of their rows is. *(Not deduping here was the original bug: it created one beneficiary per period-row → the same account on many beneficiaries → "Broj računa … je već dodeljen" on edit.)* Other maps: `DamagedEducatorPeriod → Period`, `UserDonor/User(ROLE_USER) → Donor`, `User(ROLE_DELEGATE) → Delegate`, `User(ROLE_ADMIN) → User`, `UserDelegateRequest → UserDelegateRequest` (1:1). Donor `wantsToDonateTo` constants were aligned to the legacy `SCHOOL_TYPE_*` values (`UNI=2, SCHOOL=3`) so the copy is direct. Monthly vs one-time donors is **structural** in the legacy app, not a column: a `user_donor` row = a **monthly** subscription (`/mesecna-donacija` created it, `/odjava-…` deleted it); the **one-time** flow (`/jednokratna-donacija`) created transactions directly with **no `user_donor`**. So the migration gives a `user_donor` donor a `monthly = 1` PM (amount = `user_donor.amount`) and a transaction-only donor a `monthly = 0` PM whose amount is the **sum of their legacy transactions** (`legacyTransactionSumByDonor`). Dashboard note: `Statistics::getBeneficiaryCount` counts **all** beneficiaries including `DELETED` (kept in the total for transparency; they're just no longer active).

## Frontend session (donor, later beneficiary)

`Solidarity\Frontend\Service\Session` (`packages/Frontend/src/Service/Session.php`) is the public-site analog of `Skeletor\User\Service\Session`. It reads the keys `LoginService::login($model, $entityType)` writes (`loggedIn`, `loggedInEntityType`, `loggedInRole`, `loggedInEmail`, `loggedInFirstName/LastName`) and exposes donor/beneficiary-aware accessors (`isLoggedIn`, `isDonor`, `isBeneficiary`, `getDisplayName`, lazy `getUser()` via `EntityRegistry`). Wired into `BaseAction` → every template gets `isLoggedIn` / `isDonorLoggedIn` / `currentUserName` globals, plus a `requireDonor()` redirect guard. Autowires (no bootstrap binding). Entity-type constants live in this class, so adding beneficiary is a one-liner.

## Open decisions (raised, not yet answered)

Deliberately left for a call rather than guessed at. Each is a question, not a bug report.

- **The one-time path persists no payment method.** Agreed that manual/one-time instructions should be saved with `monthly = 0` — but nothing currently writes that row. `updateDonationData` still hardcodes `monthly = 1`, and the one-time flow creates the instruction and stores nothing else. So a one-time donor leaves no record of *how* they chose to pay. Decide whether the one-time submit should also upsert a `monthly = 0` `PaymentMethod`, or whether the instruction alone is the record.
- **`donorConfirmed` doesn't exist anywhere in production.** Tests asserting on it were removed. If donor-side payment confirmation is still wanted, it needs a real column; if not, the remaining references should go.
- **`nullifyCreatedByForDelegate` is delegate-scoped, not school-scoped.** `Delegate::update()` now compensates at the call site (it reclaims the whole new school list, not just the additions, whenever a removal happened — see `DelegateSchoolDiffTest`). The narrower fix is a `nullifyCreatedByForDelegateAndSchool($delegateId, $schoolId)` so removal touches only the school removed and no reclaim is needed. Deferred because it changes a query with live data behind it.
- **Empty `paymentData` wipes a donor's payment methods.** Documented by a test, not fixed. An empty submit is currently indistinguishable from "remove everything".
- **`compileXlsxTransactionList` has no caller.** `sendTransactionListToAffectedDelegates()` is gone from `TransactionController`, and the upload half's route is not in `permissions.php`, so the whole round trip is off. Confirmed deliberate for the first production release — revisit when the delegate payout mail is wanted again. See `donation-flow.md`.
- **`Mailer::sendDashboardMagicLinkMail()` renders the wrong data key.** It passes `magicLinkUrl`; `themes/email/magicLink.php` reads only `$data['loginUrl']`, so the mail goes out with `<a href="">`. It has **no callers** — the delegate/admin dashboard login goes through the framework's `MagicLinkService` → `sendMagicLinkEmail()`, which passes `loginUrl` correctly, and that path works. So this is almost certainly leftover code. Decide whether to delete it or fix the key; either way, do not wire it up as-is. Not covered by `MailerRoutingTest` on purpose — testing it would pin behaviour that should not exist.
- **The school stats panel counts two different populations in one row.** `SchoolController::getSchoolStatsByPeriod()` excludes `Beneficiary::STATUS_DELETED` from the head count and the requested total (`b.status != :deleted`), but the four money buckets — confirmed / paid / active / cancelled — filter only on school, period and transaction status, never on beneficiary status. So a GDPR-erased person is absent from "1 person asked for 40,000" while the 5,000 already sent on their behalf still appears under confirmed, and nothing on screen explains the mismatch. Both readings are defensible (the money really did move; the person really is gone), so this needs a team call: either add `b.status != :deleted` to the four bucket queries, or label the money column as "all time, including removed records". `SchoolControllerTest::testTransactionsOfADeletedBeneficiaryStillCountTowardsTheMoney` pins the current behaviour meanwhile.
- **Six page blocks type-hint an empty marker interface for a dependency they call methods on.** `Howitworks`, `Threepillars`, `Valuecards`, `Find`, `Contactcards` and `Projectsdisplay` declare `CrudServiceInterface $imageService` and then call `$this->imageService->getById()`. `Skeletor\Core\Service\Contracts\CrudServiceInterface` **declares no methods at all** — it is a marker — so nothing but convention says the injected service has `getById`. It works because `bootstrap.php` hands each of them `Skeletor\Image\Service\Image` explicitly. Narrowing the six hints to `Image` (or whatever interface really carries `getById`) would make the requirement checkable; until then `BlockParserContractTest` stubs the concrete service rather than the declared type, and says why.
- **A period's "Max iznos" cannot be set and would do nothing if it could.** `themes/admin/period/form.php` renders a `maxAmount` input, complete with a hint about falling back to `Beneficiary::MONTHLY_LIMIT`. `Period\Filter\Period::filter()` builds its output array by hand and **does not include `maxAmount`**, so the posted value never reaches the factory — the field silently does nothing on every save. And `Period::$maxAmount` is read by no code at all: only `MigrateLegacy` writes it (as 0), and `Beneficiary\Filter` carries a matching `// todo add validation for maxAmount from project if set`. So it is an unimplemented feature wearing a working control, not a broken one. Note also that `Period\Filter` has **no validator** — the whole thing is commented out and `getErrors()` returns `[]`, so period input is unvalidated. Decide whether to finish per-period limits or drop the input from the form.
- **Nothing enforces the transaction maximum on submit.** `getPaymentMethodPreview` computes `maxAmount` from the same three constraints the allocator uses, but `Transaction\Validator\Transaction` only checks that the donor and beneficiary share a payment type — it still carries a `@TODO verify that donor has entered more than entered amount in the form`. So the preview is advisory: an admin can type any amount and it will be written. Two known gaps between the preview and the cron, both pinned by `PaymentMethodPreviewTest`: the preview applies **no 500 RSD floor** (`MIN_TRANSACTION_DONATION_AMOUNT`), and it **ignores `Donor::$wantsToDonateTo`** (the MSP school-vs-university preference). **Accepted for now** — creating instructions from the dashboard is an edge case and rarely used. Revisit if manual creation becomes routine; the fix is to move the three-way `min()` into the validator.
- **`MailerSendMailer::handleApplicationError()` can fatal while reporting a fatal.** Framework code (`vendor/dj_avolak/skeletor`), reached through the Monolog error handler. It indexes `$_SERVER['REQUEST_URI']` unguarded — absent on any CLI/cron run — and then evaluates `count($found)` on a `$found` that is only assigned inside a preceding `if`. So an error raised by the cron produces an undefined-variable/undefined-index error instead of an error mail. Same family as the Skeletor bootstrap-logging item: the reporting path is the thing that breaks. Fix belongs in the framework, not here.

## TODO / Known gaps

- **HIGH: no rate limiting on magic-link requests — donors, delegates and admin users.** `MagicLinkService::requestMagicLink()` (Skeletor) invalidates old tokens, mints a new one and sends mail on **every** call, with no cooldown anywhere in the codebase — the only throttle that exists is `touchLastVisit`, which is unrelated. Reachable publicly through `Donor::requestMagicLink()`, `DelegateLoginController::requestMagicLink()` and `Skeletor\Login\Controller\LoginController::requestMagicLink()` (`/login/user/{action}`). Three consequences: anyone can flood a known donor's inbox; `findByEmail` throwing `NotFoundException` for unknown addresses turns the endpoint into an **enumeration oracle** for the donor list; and unbounded sends run up MailerSend cost and risk the sending domain being throttled — which locks *everyone* out, since magic link is the only login path. **Captcha cannot be the answer**: the config key is read by `LoginController` (so it must stay or admin login fatals) but **no template renders `captchaSiteKey`**, `ContactFormAction` is not routed, and the forgot/reset password forms have their captcha lines commented out — it is inert. Fix: per-email and per-IP cooldown in front of `requestMagicLink` (Redis is already in the container; `SETEX` on the email with a 60s TTL), plus returning the same response whether or not the address exists, to close the enumeration side. Belongs in Skeletor, but do it app-side first so launch does not wait on a framework release.
- **A stale session is a 500, not a redirect to login.** `AuthMiddleware` (Skeletor) does `$this->sessionManager->getStorage()->clear()` and then `$this->flash::error('Invalid session. Please log in again.')` on the *next line*. `clear()` calls `fromArray([])` → `$_SESSION = []`, which removes `flash_messages`; but `Flash` is a container singleton whose constructor seeded that key once at build time, so `SessionManager::getSession()` then returns null against an `array` return type and throws. Any user whose `loggedIn` id no longer resolves — **every admin and delegate holding a cookie across the production cutover** — gets a fatal instead of the login page. Fix is a one-line reorder in the framework (flash before clear, or re-seed the key after). **Mitigation without a framework release: invalidate all sessions at cutover** by changing the session cookie name, or clearing the session store, so nobody carries a pre-migration session into the new data.

- **`updateStatusBulk` reports the last row, not the batch.** `$success` and `$message` are reassigned on every loop iteration while `$returnStatus` is sticky once anything fails, so the response describes whichever id happened to be processed last. Put a locked transaction first and a fresh one second and the caller gets **HTTP 500 alongside `success: true`** and "Transakcija su potvrđene."; reverse the order and the same batch reports failure. Neither response says *which* rows were refused — `$failed` is collected and then discarded. Fix: accumulate per-id outcomes and return them (`['updated' => [...], 'failed' => [id => reason]]`), and derive `success`/status from the totals rather than from the last iteration. Both orderings are pinned by `UpdateTransactionStatusTest` so the behaviour can't drift unnoticed before then.
- **An empty bulk selection returns HTTP 200.** `$returnStatus` is initialised to 200 and the outer catch in `updateStatusBulk` sets `success = false` without touching it, so "No ids provided." comes back on a 200. A caller checking only the status code reads it as a success. One-line fix whenever the above is done.
- **Sync session data when an entity is saved in the dashboard.** `LoginService::login()` snapshots `loggedInEmail`, `loggedInFirstName/LastName`, `loggedInRole` (and `tenantId`) into the session at login time. When an admin edits that entity in the backend (or a donor edits their own profile) — name, email, role, status — the session copy goes **stale** until the next login. The cheap `Session` getters (`getDisplayName`, `getEmail`, `getRole`) and the `BaseAction` template globals read these snapshots, so a logged-in donor can see an outdated name/email after a dashboard edit. `getUser()` reloads fresh from the DB and is unaffected. Fix: on entity save in the dashboard, refresh the matching session keys for any active session of that entity (or store less in-session and read more from `getUser()` where freshness matters). Needs a session-by-entity lookup since the editor's session ≠ the affected entity's session.
- ~~**Delegate editing a beneficiary — project dropdown can render empty and drop the row on save.**~~ **Resolved** by making `syncRegisteredPeriods()` reconcile by id and fall back to stored values instead of rebuilding the list (see `patterns.md` 12b). The dropdown can still render empty for a delegate whose assigned projects omit the registration's project — that is now cosmetic, not destructive. Filling the dropdown as well (merging the registration's own project into `$assignedProjects`, mirroring the period merge) is still available if the empty select proves confusing; it was deliberately not done, to avoid showing delegates projects they do not hold.
- **[superseded, kept for context] Delegate editing a beneficiary with an inactive-period registration — project dropdown can render empty.** `BeneficiaryController::form()` now merges a beneficiary's own registered periods into the *period* dropdown even when inactive (fixing the empty "Izaberite Period" + save-drops-data bug, gotcha #11 in `patterns.md`). But the *project* dropdown is still built only from the editor's assigned projects (`$assignedProjects`). For an **admin** that's all projects, so fine; for a **delegate**, if the registration's project isn't among their assigned projects the project `<option>` won't preselect → shows empty, and the same delete-on-save risk applies to that row. Fix: apply the same merge to the project list — add each `registeredPeriods` row's own project to `$assignedProjects` when missing (near the period merge in `form()`). Low priority (delegates rarely hold inactive-period beneficiaries), but it's the matching half of the period fix.
- **Transaction edit form: render period as read-only text instead of an injected Select option.** A transaction's period is immutable after creation (`TransactionFactory::compileEntityForUpdate` writes only `status`/`comment`) and the edit form already shows the field `readOnly`. The current fix merges the transaction's own (possibly non-`active`) period into the `Select` collection so it displays — a bit of a hack, since the create path deliberately lists `active` periods only (admins must not create transactions for non-active periods). Cleaner: on edit (`dataAction !== 'create'`) render the period as a **read-only text field** showing `period->getLabel()` (like Amount/Donor/Beneficiary already are) and drop the merge in `TransactionController::form()`; keep the create path's active-only `Select` untouched. Fully separates "create = pick an active period" from "edit = just display the stored one". Low priority — current behaviour is correct, this is a cleanup.
